# 멤버 검색 — 기술스택 OR 매칭

요청한 기술스택 중 **하나라도 보유한** 회원을 검색하는 기능. 모든 스택을 보유해야 매칭되는 기존 팀원 찾기(AND 매칭, `/api/v1/members/search`)와 구분되는 별도 검색이다.

> **구현 상태 (2026-11-27)**: 현재 구현은 **검색 전용 투영 테이블(대안 4)** 방식이다 — V9 마이그레이션, `MemberStackSearchProjector`, 네이티브 한 문장 쿼리. 초기 구현(비상관 IN 세미조인)의 설계 근거("쿼리 설계 근거" 섹션)와 실험 기록은 전환 결정의 근거로 보존한다. 정렬은 projectCount 내림차순 고정(sort 파라미터 무시).

## API

```
GET /api/v1/members/search/tech-stacks?techStackNames=React,Spring&page=0&size=10&sort=projectCount,desc
```

| 파라미터 | 필수 | 설명 |
|---|---|---|
| `techStackNames` | O | 기술스택 이름 목록. 하나라도 보유하면 매칭 |
| `pageable` | X | 페이징/정렬. `projectCount,desc`(프로젝트 경험순), `realName,asc`(이름순) |

응답은 기존 팀원 찾기와 동일한 `MemberCardResponse` 페이지.

## 패키지 구조

검색 전용 쿼리를 member 도메인 하위의 별도 패키지로 분리했다.

```
domain/member/search/
├── MemberTechStackSearchService.java        # 서비스 인터페이스
├── MemberTechStackSearchServiceImpl.java    # 이름→ID 변환 + 검색 오케스트레이션
├── MemberTechStackSearchRepository.java     # 투영 테이블 네이티브 한 문장 쿼리
├── MemberStackSearch.java                   # 투영 테이블 엔티티 (테스트 ddl-auto용 스키마 매핑)
└── MemberStackSearchProjector.java          # 투영 동기화 (멱등 재투영/행 제거)

web/member/controller/
└── MemberSearchController.java              # GET /api/v1/members/search/tech-stacks
```

동기화 호출 지점: 가입(`AuthService.sejongRegister`)·프로필 스택 수정(`MemberProfileServiceImpl`) → `rebuildFor`, 탈퇴/삭제(`AuthService`) → `removeFor`, 프로젝트 참여/탈퇴 → `MemberRepository.increase/decreaseProjectCount`가 투영의 project_count를 같은 트랜잭션에서 미러 갱신.

## 동작 흐름

1. **입력 검증**: `techStackNames`가 비어 있으면 `INVALID_REQUEST`(400).
2. **이름 → ID 선변환**: 이름 중복을 제거한 뒤 `tech_stack` 테이블에서 ID를 조회한다. 검색 쿼리에서 `tech_stack` 조인을 제거하기 위함 (v1 검색과 동일한 방침).
3. **존재하지 않는 이름은 무시**: AND 검색과 다른 지점. AND에서는 없는 이름이 하나라도 있으면 결과가 있을 수 없어 빈 페이지를 반환하지만, OR에서는 없는 이름이 결과를 좁히지 않으므로 무시하고 나머지 이름으로 검색한다. **전부** 존재하지 않을 때만 쿼리 없이 빈 페이지를 반환한다.
4. **OR 매칭 조회**: 소프트 삭제(`deleted_at IS NULL`) 필터 + 세미조인으로 페이징 조회.
5. `MemberCardResponse::from`으로 매핑해 반환.

## 트랜잭션에서 실행되는 SQL

`@Transactional(readOnly = true)` 안에서 아래 순서로 실행된다.

### 1. 기술스택 이름 → ID 변환

`TechStackRepository.findByNameIn(distinctNames)`

```sql
SELECT ts.tech_stack_id, ts.name, ...
FROM tech_stack ts
WHERE ts.name IN ('React', 'Spring');
```

### 2. 회원 조회 (본문 쿼리 — 한 문장, DB 왕복 1회)

`MemberTechStackSearchRepository.findMembersHavingAnyTechStack(techStackIds, pageable)` — 스택별로 투영 테이블 상위 (offset+limit)명을 인덱스 순서로 읽고(UNION이 중복 보유자 제거), 확정된 소수 ID만 member에 PK 조인한다.

```sql
SELECT m.* FROM (
  (SELECT member_id, project_count FROM member_stack_search
   WHERE tech_stack_id = 1 ORDER BY project_count DESC, member_id LIMIT 10)
  UNION
  (SELECT member_id, project_count FROM member_stack_search
   WHERE tech_stack_id = 5 ORDER BY project_count DESC, member_id LIMIT 10)
) t
JOIN member m ON m.member_id = t.member_id
ORDER BY t.project_count DESC, t.member_id
LIMIT 10 OFFSET 0;
```

실측(230k 회원): 인기 스택 2.97ms / 희소 스택 0.88ms — 스택 분포와 무관하게 상한 보장.

### 3. 전체 건수 조회 (count 쿼리)

결과가 페이지 크기보다 작아 총 건수를 확정할 수 있으면 `PageableExecutionUtils`가 실행을 생략한다.

```sql
SELECT COUNT(DISTINCT member_id)
FROM member_stack_search
WHERE tech_stack_id IN (1, 5);
```

여러 스택 보유자의 중복 집계를 막는 DISTINCT 때문에 보유 행 수에 비례하는 비용이 들며(인기 스택 실측 59.6ms — 세미조인 시절 count 102~135ms보다는 개선), 전체 검색 비용의 지배 항이다. 더 줄이려면 total 없는 무한 스크롤(Slice) 전환이 필요한데 이는 API 계약 변경이라 프론트 합의가 선행돼야 한다.

## 쿼리 설계 근거 (초기 구현 — 세미조인, 현재는 대안 4로 전환)

초기 구현은 **비상관 IN 서브쿼리(세미조인)** 를 선택했다. 아래 비교는 그 시점의 판단 기록이며, 실험에서 세미조인 전략 선택의 맹점이 확인되어 대안 4로 전환했다.

- 서브쿼리의 `tech_stack_id IN (...)` 범위 스캔이 커버링 인덱스 `idx_member_tech_stack_stack_member(tech_stack_id, member_id)`로 **index-only** 처리된다.
- MySQL이 `IN (서브쿼리)`를 세미조인(Materialization / FirstMatch)으로 최적화하면서 중복 `member_id`를 알아서 제거하므로 별도 `DISTINCT`가 필요 없다.
- 희소한 스택으로 검색할 때 옵티마이저가 "스택 → 멤버" 방향으로 드라이빙할 수 있다.

### 검토했지만 사용하지 않은 대안

#### 대안 1 — JOIN + DISTINCT

```sql
SELECT DISTINCT m.*
FROM member m
JOIN member_tech_stack mts ON mts.member_id = m.member_id
WHERE m.deleted_at IS NULL
  AND mts.tech_stack_id IN (1, 5);
```

JOIN의 계약은 "매칭되는 모든 조합을 행으로 만들어라"다. 우리 질문("보유 여부")보다 큰 답을 만들었다가(스택 k개 매칭 회원이 k행으로 복제) DISTINCT로 도로 지우는 구조라, count 쿼리도 `COUNT(DISTINCT ...)`로 비싸진다.

정확히 말하면 항상 느린 건 아니다 — SELECT 컬럼이 전부 member 소속이면 MySQL이 "조합 정보는 어차피 버려질 운명"임을 알아채고 세미조인처럼 실행해주는 특수 최적화가 있다. 문제는 **잘 돌 때는 IN 세미조인과 동점이고, 그 최적화가 깨지는 순간(스택 주도 선택, SELECT에 mts 컬럼 추가 등) 전체 행 임시테이블 dedup + filesort로 떨어진다**는 것. 하한은 같고 상한만 나쁜 선택이라 쓰지 않았다. IN은 "존재만 확인하면 된다"는 의도를 옵티마이저에 직접 전달하므로 특수 최적화에 기댈 필요가 없다.

#### 대안 2 — 스택별 상관 EXISTS를 OR로 체이닝

```sql
SELECT m.*
FROM member m
WHERE m.deleted_at IS NULL
  AND (
      EXISTS (SELECT 1 FROM member_tech_stack mts
              WHERE mts.member_id = m.member_id AND mts.tech_stack_id = 1)
   OR EXISTS (SELECT 1 FROM member_tech_stack mts
              WHERE mts.member_id = m.member_id AND mts.tech_stack_id = 5)
  );
```

AND 매칭(`MemberRepositoryImpl.techStackIdsExist`)의 대칭형. AND에서는 하나라도 실패하면 즉시 탈락하는 short-circuit 이득이 있지만, OR에서는 반대로 **매칭 안 되는 회원일수록 N개 서브쿼리를 전부 평가**하게 된다. IN 하나로 합치면 의미는 같고 서브쿼리는 한 번이다.

#### 대안 3 — 상관 EXISTS + IN

```sql
SELECT m.*
FROM member m
WHERE m.deleted_at IS NULL
  AND EXISTS (
      SELECT 1 FROM member_tech_stack mts
      WHERE mts.member_id = m.member_id
        AND mts.tech_stack_id IN (1, 5)
  );
```

결과는 동치지만 상관 서브쿼리라 항상 "멤버 → 스택" 방향으로만 탐색한다. 비상관 IN은 옵티마이저가 양방향 중 유리한 쪽을 고를 수 있다.

#### 대안 4 — 검색 전용 테이블 (읽기 모델) — ✅ 채택 (2026-11-27)

실험(아래 "재측정" 참고)에서 드러난 모든 문제 — 드라이빙 방향 선택, Materialize↔FirstMatch 맹점, 규모에 따라 움직이는 손익분기점 — 는 전부 "옵티마이저에게 선택권이 있어서" 생긴다. 검색 쿼리 모양에 정확히 맞춘 투영 테이블을 두면 선택할 것이 없는 쿼리가 되어 이 문제 계급 자체가 소멸한다. #385가 최종적으로 간 방향(place_stats 읽기 모델)이기도 하다.

```sql
CREATE TABLE member_stack_search (
    tech_stack_id  BIGINT NOT NULL,
    project_count  INT    NOT NULL,
    member_id      BIGINT NOT NULL,
    PRIMARY KEY (tech_stack_id, project_count DESC, member_id)
);
```

- `deleted_at` 컬럼이 없다 — 탈퇴 회원은 행을 지운다. 검색 가능한 회원만 존재하는 테이블.
- 보조 인덱스 없이 **클러스터드 PK가 곧 쿼리**: 스택별 `WHERE tech_stack_id = ? ORDER BY project_count DESC LIMIT 10` = PK 순방향 10행 스캔.
- OR 매칭은 스택별 top-(offset+limit)을 UNION으로 병합하고, 회원 카드 정보는 같은 문장 안에서 확정된 ~10개 ID를 member에 조인해 가져온다(PK 10회 lookup — 상한 보장, 네트워크 왕복 증가 없음):

```sql
SELECT m.* FROM (
  (SELECT member_id, project_count FROM member_stack_search
   WHERE tech_stack_id = 30 ORDER BY project_count DESC LIMIT 10)
  UNION
  (SELECT member_id, project_count FROM member_stack_search
   WHERE tech_stack_id = 33 ORDER BY project_count DESC LIMIT 10)
) t
JOIN member m ON m.member_id = t.member_id
ORDER BY t.project_count DESC LIMIT 10;
```

로컬 실측(230,003명, 실험 잔해 인덱스 `idx_mts_stack_active_pc`로 모사): 인기 2.86ms / 희소 0.53ms — 최속(FirstMatch 0.116ms)은 아니지만 **어느 구간에서든 상한이 보장**된다. 이 방식의 가치는 "가장 빠름"이 아니라 "절대 느려지지 않음"이다.

동기화는 경로별 UPDATE 수술 대신 멱등 재투영 하나로 통일한다:

```
rebuildFor(memberId):
    DELETE FROM member_stack_search WHERE member_id = ?
    INSERT ... SELECT (활성 회원이면: 현재 스택 × 현재 project_count)
```

트리거 이벤트는 ① 프로필 스택 수정 ② 프로젝트 참여/탈퇴(project_count 변경) ③ 회원 탈퇴/복구 — 전부 기존 이벤트 지점이 있는 경로고, 검색의 수 초 지연은 수용 가능하므로 커밋 후 비동기로 처리한다. 파생 데이터라 전체 재구축(백필)과 야간 정합성 검증이 가능하다.

**채택 기록 (2026-11-27)**: 230k 실험에서 세미조인 전략 선택의 450배 맹점이 확정된 뒤 이 방식으로 전환했다. 구현: V9 마이그레이션(테이블+백필), `MemberStackSearchProjector`(가입·스택 수정 → 재투영, 탈퇴·삭제 → 행 제거), `MemberRepository` 카운터 default 메서드(project_count 미러). 전환 실측(230k): 본문 쿼리 인기 2.97ms / 희소 0.88ms, count 59.6ms(기존 102~135ms 대비 개선, 여전히 지배 항 — 무한 스크롤 전환은 API 계약 변경이라 보류). 남은 트레이드오프: 정렬이 projectCount DESC로 고정(sort 파라미터 무시), 깊은 OFFSET은 스택별 offset+limit 읽기라 선형 증가.

## 정렬 인덱스와 두 가지 실행 계획

`ORDER BY project_count DESC LIMIT 10`이 붙는 순간, 옵티마이저 앞에는 **비용 축이 서로 반대인** 두 계획이 놓인다.

| | 계획 A — 스택 주도 | 계획 B — 멤버 주도 |
|---|---|---|
| 동작 | 보유자 전원 수집 → 전부 정렬 → LIMIT | 정렬 인덱스 순서로 스캔하며 보유 확인 → 페이지 차면 **조기 종료** |
| 비용 축 | 보유자 수 N에 비례 | 10 ÷ 보유율 (훑은 행 수) |
| 유리한 구간 | 희소 스택 (보유자 적음) | 인기 스택 (보유율 높음) |
| 쓰는 인덱스 | `idx_member_tech_stack_stack_member` | `idx_member_deleted_project_count` + `uk_member_tech_stack_pair` |

계획 B는 `member(deleted_at, project_count)` 정렬 인덱스가 있어야만 존재한다. 그래서 **V8 마이그레이션**으로 `idx_member_deleted_project_count`를 추가했다 (메인페이지 `findAllWithProjectCountSort`는 필터가 `deleted_at IS NULL`뿐이라 이 인덱스만으로 항상 조기 종료 — 선택 갈등 없는 순수 이득).

남는 질문은 "옵티마이저가 구간별로 올바른 계획을 고르는가"였다. 참고한 사례인 [SOLPLY#385](https://github.com/SOLPLY/SOLPLY-SERVER/issues/385)는 MySQL 코스트 모델이 **LIMIT 조기 종료 이득을 비용 계산에 반영하지 않아** (조인 순서는 전체 결과 생산 비용 기준으로 먼저 확정되고, LIMIT 보정은 그 위의 사후 단계) 광역+인기 태그 구간에서 3배 빠른 계획을 못 고르는 문제를 보고했다. 우리도 같은 함정이 있는지 실측으로 확인했다.

## 실험 기록 (2026-11-27, 로컬 MySQL)

환경: 회원 70,003명(활성 68,488), member_tech_stack 147,839행. 인기 스택 = Java+Spring Boot(보유 28,872행, 매칭 16,991명), 희소 스택 = MLflow+CUDA(보유 133행, 매칭 124명). 본문 쿼리 + `ORDER BY project_count DESC LIMIT 10`을 `EXPLAIN ANALYZE`로 측정 (워밍업 후 2회차 값).

| 구간 | 계획 | 실측 |
|---|---|---|
| 인기 (Java+Spring) | 인덱스 없음: 전체 스캔 + 68,488명 filesort | 61.3ms |
| 인기 | **인덱스 후 옵티마이저 선택**: 멤버 주도 27행 조기 종료 + 서브쿼리 Materialize | **9.1ms** |
| 인기 | 멤버 주도 + FirstMatch 강제 (`SEMIJOIN(FIRSTMATCH)` 힌트) | 1.95ms |
| 희소 (MLflow+CUDA) | **옵티마이저 선택**: 스택 주도 weedout (인덱스 전후 동일) | **0.45ms** |
| 희소 | 멤버 주도 강제 — 10명 못 채워 4,277행 스캔 | 29.6ms |

### 해석

1. **드라이빙 방향 선택은 옵티마이저가 양 구간 모두 올바르게 해냈다.** 인덱스를 추가하자 인기 스택은 멤버 주도(27행 조기 종료)로 갈아탔고(61.3 → 9.1ms), 희소 스택은 스택 주도를 유지했다. #385의 병리(조기 종료 계획을 못 고름)는 우리 데이터 형태에서는 재현되지 않았다 → **조건부 힌트 불필요.**
2. **2차 격차는 남아 있다.** 인기 스택에서 멤버 주도를 고르고도 멤버십 확인을 보유자 16,991명 전체 Materialize(9.05ms, 전체 시간의 대부분)로 수행한다. 27명만 `uk_member_tech_stack_pair`로 직접 probe하는 FirstMatch가 4.7배 빠르지만(1.95ms), 절대값 9.1ms는 수용 범위고 힌트는 QueryDSL에서 네이티브 전환이 필요해 **현재는 개입하지 않는다.**
3. **한쪽 고정이 왜 안 되는지도 실측으로 확인됐다.** 희소 스택에 멤버 주도를 강제하면 10명을 채우지 못해 4,277행을 스캔, 63배 느려진다(0.45 → 29.6ms). #385가 전역 힌트를 기각한 근거("결과 0건 태그 75배")와 같은 모양이다. 같은 이유로 "서브쿼리를 앱에서 별도 실행해 ID 목록을 IN으로 넘기는" 분리안도 기각 — 계획 A를 코드에 고정하는 것과 같고, 인기 스택에서 ID 수천 개를 왕복 운반하게 된다.

### 추가 측정 — 회원 170,003명으로 증설 (같은 날)

"로컬 성능이 너무 좋아 보인다"는 의심에 기존 분포를 복제해 회원을 10만 명 추가(member_tech_stack 총 ~44만 행, Java+Spring 보유 74,956행)하고 재측정했다. 예상(비용이 데이터에 비례해 ~30ms)과 반대의 결과가 나왔다:

| 구간 | 70,003명 | 170,003명 |
|---|---|---|
| 인기 (Java+Spring) | 9.1ms (멤버 주도 + **Materialize**) | **0.4~0.6ms** (멤버 주도 + **FirstMatch**, 31행 조기 종료) |
| 희소 (MLflow+CUDA) | 0.45ms (스택 주도) | 3.9ms (스택 주도, 보유 340행으로 증가) |

데이터가 커지자 옵티마이저가 Materialize(보유자 전체 임시테이블)를 버리고 FirstMatch(회원별 `uk_member_tech_stack_pair` 직접 probe)로 갈아탔다. 인기 구간이 데이터 증가에도 빨라진 이유가 계획 B의 본질이다: 멤버 주도 조기 종료의 비용은 10 ÷ 보유율이라 **회원 수와 무관**하다(70k에서도 27행, 170k에서도 31행만 스캔). 반면 희소 구간(계획 A)은 보유자 수에 비례해 0.45 → 3.9ms로 늘었다 — 두 계획의 비용 축이 반대라는 모델 그대로의 결과.

### 재측정 — 230,003명 복원 후 전략 선택 맹점 확정

170k에서 "격차가 해소됐다"는 해석이 맞는지 230k로 복원해 재검증했다. 결과: **해소된 게 아니라 손익분기점의 위치 문제였다.**

| 규모 | 옵티마이저 선택 (인기) | 실측 | FirstMatch 강제 | 격차 |
|---|---|---|---|---|
| 70,003 | Materialize | 9.1ms | 1.95ms | 4.7배 |
| 170,003 | **FirstMatch** | 0.4ms | (= 선택됨) | — |
| 230,003 | **Materialize** | 51.9ms | **0.116ms** | **~450배** |

230k에서 옵티마이저는 다시 Materialize로 돌아갔다: 회원 스캔은 22행에서 조기 종료했지만, 그 전에 보유자 57,677명 ID 임시테이블 구축에 51.8ms를 쓴다. FirstMatch를 강제하면 22행 × probe로 0.116ms — 같은 질문을 450배 비싸게 답한 것이다.

원인은 드라이빙 방향이 아니라 **세미조인 전략 선택에 남아 있는 같은 맹점**이다. 옵티마이저는 Materialize vs FirstMatch를 비교할 때 회원 스캔이 끝까지 돈다고 가정한다(LIMIT 조기 종료 미반영). 그래서 회원 수 추정치가 클수록 "명단을 한 번 만들어 상각"하는 Materialize가 유리해 보이고, 그 모델상 손익분기점이 170k~230k 사이에 있었던 것뿐이다. 실제로는 조기 종료 때문에 회원을 ~22행만 읽으므로 FirstMatch가 어느 규모에서든 압승이다.

결론 수정: 드라이빙 방향(계획 A↔B) 선택은 옵티마이저가 전 구간에서 올바르게 하지만, **인기 스택 구간의 세미조인 전략(Materialize↔FirstMatch)은 규모에 따라 틀릴 수 있고 격차가 규모에 비례해 커진다**(회원 수 × 보유율에 비례). 현재 실서비스 규모(수천 명)에서는 어느 전략이든 ms 미만이라 개입하지 않지만, 회원 수만 단위 진입 시 `SEMIJOIN(FIRSTMATCH)` 힌트 적용(네이티브 쿼리 전환 필요)을 1순위 후보로 둔다.

재검토 트리거: 인기 스택 p99가 눈에 띄게 늘거나 회원 수가 수만 단위로 커지면 실행 계획(특히 Materialize ↔ FirstMatch 선택)을 다시 채취한다.

> **로컬 DB 스키마 드리프트 주의**: 로컬 `member_tech_stack`에는 코드에 없는 비정규화 컬럼(`member_deleted_at`, `project_count`)과 인덱스 `idx_mts_stack_active_pc`, 그리고 `member`에 `idx_member_active_pcount`(실험 중 V8 정식 명칭으로 교체됨)가 이전 실험의 흔적으로 존재했다. 측정은 해당 ad-hoc 인덱스를 `IGNORE INDEX`로 배제한 값과 교차 확인했다(계획·수치 동일). 코드 기준 스키마가 정본이다.
