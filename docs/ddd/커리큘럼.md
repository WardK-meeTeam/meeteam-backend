# MeeTeam DDD 적용 커리큘럼

> 본 문서는 MeeTeam Backend에 **도메인 주도 설계(Domain-Driven Design)** 를 점진적으로 도입하기 위한
> 학습 + 실전 적용 로드맵이다. 단순 이론 학습이 아니라, 각 단계마다 **현재 프로젝트의 어떤 코드를
> 어떻게 바꿀지**를 함께 정의해 "공부 따로, 적용 따로"가 되지 않도록 한다.

---

## 0. 들어가기 전에 — 왜 DDD인가, 그리고 현재 우리는 어디 있는가

### 현재 프로젝트 진단 (출발점)

MeeTeam은 이미 DDD에 가까운 구조적 자산을 일부 갖추고 있다.

| 이미 갖춘 것 | 위치 | DDD 개념 |
|---|---|---|
| 도메인별 패키지 분리 | `domain/{project, member, recruitment, ...}` | Bounded Context 후보 |
| Command/Query 서비스 분리 | `ProjectCommandService` / `ProjectQueryService` | CQRS 맹아 |
| 값 객체 패키지 | `project/vo/RecruitmentDeadline` | Value Object |
| Command DTO | `service/dto/ProjectPostCommand` 등 | 입력 모델 분리 |
| 도메인 서비스 흔적 | `recruitment/service/RecruitmentDomainService` | Domain Service |
| 이벤트 기반 알림 | `@TransactionalEventListener` + `@Async` | Domain Event |
| 표준 응답/예외 | `SuccessResponse`, `CustomException` | (보조 인프라) |

### 아직 부족한 것 (이번 커리큘럼으로 메울 것)

- **빈약한 도메인 모델(Anemic Domain Model)**: 엔티티가 getter/setter 덩어리이고 비즈니스 규칙이 Service에 흩어져 있을 가능성.
- **Aggregate 경계 불명확**: `Project`, `Recruitment`, `RecruitmentState`, `ProjectMember` 사이의 일관성 경계와 참조 방식(객체 참조 vs ID 참조)이 정리되지 않음.
- **유비쿼터스 언어 부재**: 코드 용어(영문)와 도메인 용어(한글) 매핑 사전이 없음.
- **계층/의존 방향**: 도메인이 인프라(JPA, S3 등)에 직접 의존. 의존 역전(DIP)·ACL 미적용.

### 핵심 원칙 (전 과정 공통)

1. **테스트로 보호하고 리팩터링한다.** DDD 적용은 곧 리팩터링이다. 안전망 없이 손대지 않는다.
2. **한 번에 한 Bounded Context씩.** 전체를 갈아엎지 않는다. `project`/`recruitment`를 파일럿으로.
3. **문서 → 모델 → 코드 순서.** 용어 사전과 이벤트 스토밍 결과물이 패키지 구조의 근거가 된다.

## 학습/적용 진행 방식

각 단계는 **[학습]** 과 **[MeeTeam 적용]** 으로 구성된다.

- **[학습]**: 개념을 짧게 정리하고 예제로 손에 익힌다.
- **[MeeTeam 적용]**: 그 개념을 실제 우리 코드 어디에 적용할지, 산출물(Deliverable)은 무엇인지 정의한다.

> 산출물 문서는 모두 `docs/ddd/` 하위에 쌓는다. (예: `docs/ddd/glossary.md`, `docs/ddd/event-storming.md`)

# PART 1. 도메인 주도 설계 이해

## 1-1. DDD 등장 배경 / 레거시 코드

- **[학습]** DDD가 풀려는 문제: 복잡한 도메인에서 코드와 현실(비즈니스 언어)의 괴리, 비대해지는 Service, 변경에 취약한 구조.
- **[학습]** 레거시 코드의 정의(테스트 없는 코드)와 그것이 DDD 적용을 막는 이유.
- **[MeeTeam 적용]** 현재 "신의 서비스(God Service)" 후보 식별. `ProjectEditServiceImpl`, `ProjectManagementServiceImpl` 등의 책임 과다 여부를 점검하고 목록화.
  - 📄 산출물: `docs/ddd/legacy-assessment.md` (리팩터링 위험/우선순위 표)

## 1-2. 유연한 설계 — ASSERTION

- **[학습]** 사전조건/사후조건/불변식(invariant) 개념. 객체가 스스로 자신의 유효 상태를 보장한다.
- **[MeeTeam 적용]** `Project`, `Recruitment` 생성/수정 시 만족해야 할 불변식 정의.
  - 예: "모집 마감일은 생성 시점 이후여야 한다", "모집 정원은 1 이상", "마감된 모집에는 지원 불가".
  - 현재 Service에 흩어진 검증을 엔티티/VO의 생성자·메서드 안으로 이동할 후보 도출.

# PART 2. JUnit 5 & 테스트 안전망

> 프로젝트엔 이미 `docs/TEST_CONVENTION.md`와 H2 기반 테스트가 있다. 이를 DDD 리팩터링의 안전망으로 강화한다.

## 2-0. JUnit 5 학습
- **[학습]** `@Test`, `@DisplayName`, `@Nested`, `@ParameterizedTest`, AssertJ, 테스트 더블(Mockito).
- **[MeeTeam 적용]** `docs/TEST_CONVENTION.md` 재확인 및 부족한 부분 보완.

## 2-1. 문자열 덧셈 계산기 (TDD 워밍업)
- **[학습]** TDD 사이클(Red-Green-Refactor)을 작은 문제로 체득.
- **[MeeTeam 적용]** 별도 적용 없음. 순수 학습용. (원하면 `vo/RecruitmentDeadline` 같은 작은 VO를 TDD로 재작성하며 연습)

## 2-2. 요구 사항 정리
- **[학습]** 기능 명세를 테스트 가능한 단위로 쪼개기.
- **[MeeTeam 적용]** 파일럿 컨텍스트(프로젝트 모집)의 핵심 유스케이스를 글머리표로 정리.
  - 예: 프로젝트 생성 → 모집 등록 → 지원 → 승인/거절 → 멤버 합류 → 모집 마감.

## 2-3. 테스트를 통한 코드 보호 (Characterization Test)
- **[학습]** 리팩터링 전, 현재 동작을 고정하는 **특성화 테스트** 작성.
- **[MeeTeam 적용]** 파일럿 도메인의 핵심 시나리오에 대해 서비스 레벨 테스트를 먼저 채워 넣는다. **이 단계가 끝나야 PART 5 이후 리팩터링 시작 가능.**
  - 📄 산출물: 파일럿 도메인 테스트 커버리지 확보 (그린 상태 확인)

# PART 3. 전략적 설계 (Strategic Design)

## 3-1. 크게 소리 내어 모델링하기 / UBIQUITOUS LANGUAGE
- **[학습]** 도메인 전문가와 개발자가 **같은 단어**를 쓴다. 코드·DB·문서·대화의 용어 일치.
- **[MeeTeam 적용]** 핵심 용어 사전 작성. 한글 도메인 용어 ↔ 코드 영문 식별자 매핑.
  - 예: 모집=`Recruitment`, 모집 상태=`RecruitmentState`, 직군=`Job`, 기술 스택=`TechStack`/`Skill`, 프로젝트 멤버=`ProjectMember`, 지원자=`Applicant`.
  - ⚠️ 현재 `skill`과 `job-tech-stack`, `recruitment`와 `recruitmentState` 등 **용어 중복/혼선** 정리 필요.
  - 📄 산출물: `docs/ddd/glossary.md`

## 3-2. BOUNDED CONTEXT
- **[학습]** 모델이 일관되게 통용되는 경계. 같은 단어라도 컨텍스트마다 의미가 다를 수 있음(예: '멤버' = 회원 vs 프로젝트 참여자).
- **[MeeTeam 적용]** 현재 `domain/*` 패키지를 Bounded Context 후보로 보고 경계와 관계를 그린다.
  - 후보: **회원(Member)**, **프로젝트/모집(Project & Recruitment)**, **지원(Application/Applicant)**, **채팅(Chat)**, **알림(Notification)**, **Q&A**, **리뷰**.
  - Context Map 작성: 어떤 컨텍스트가 어떤 컨텍스트에 의존하는지, 관계 유형(Partnership, Customer-Supplier, Conformist, ACL 등).
  - 📄 산출물: `docs/ddd/context-map.md`

# PART 4. 이벤트 스토밍 (Event Storming)

## 4-1. 용어 사전 만들기
- **[학습]** 이벤트 스토밍의 도메인 이벤트(주황), 커맨드(파랑), 애그리거트(노랑), 정책(보라) 표기법.
- **[MeeTeam 적용]** PART 3-1의 glossary를 이벤트 스토밍 표기와 연결.

## 4-2. 모델링 하기
- **[학습]** "무슨 일이 일어났는가(이벤트)"부터 역추적해 커맨드·애그리거트·정책을 배치.
- **[MeeTeam 적용]** 파일럿(프로젝트 모집) 플로우를 이벤트 흐름으로 도식화.
  - 예: `프로젝트가_생성됨` → `모집이_등록됨` → `지원이_접수됨` → `지원이_승인됨` → `프로젝트멤버가_합류함` → `모집이_마감됨`.
  - 기존 알림 이벤트(`@TransactionalEventListener` 대상)와 매핑.
  - 📄 산출물: `docs/ddd/event-storming.md`

## 4-3. 기능 우선 패키지 구성하기
- **[학습]** 기술 계층(controller/service/repo) 우선이 아니라 **기능/도메인 우선** 패키지 구성.
- **[MeeTeam 적용]** 이벤트 스토밍 결과를 토대로 목표 패키지 구조(안)를 정의. 예: 각 도메인 내부를 `application`(유스케이스) / `domain`(모델) / `infrastructure`(JPA·외부연동) / `presentation`(controller)으로 재배치할지 검토.
  - 📄 산출물: `docs/ddd/target-package-structure.md`

# PART 5. 전술적 설계 (Tactical Design)

> 여기서부터 본격적인 코드 리팩터링. PART 2-3의 테스트 안전망이 전제.

## 5-1. ENTITY와 VALUE OBJECT
- **[학습]** Entity(식별자로 구분, 가변) vs VO(값으로 구분, 불변). 빈약한 모델 → 풍부한 모델로.
- **[MeeTeam 적용]**
  - VO 후보 추출: 마감일(`RecruitmentDeadline` 이미 존재 ✅), 정원, 모집 상태, 직군+기술 묶음 등.
  - `Member`, `Project` 엔티티의 setter 제거 → 의미 있는 행위 메서드로 대체(`Project.close()`, `Recruitment.apply()` 등).
  - 📄 산출물: 리팩터링 1차 (Project/Recruitment 엔티티)

## 5-2. AGGREGATE
- **[학습]** 일관성 경계, Aggregate Root, "한 트랜잭션은 하나의 Aggregate만 변경", Aggregate 간 **ID 참조** 권장.
- **[MeeTeam 적용]** 가장 중요한 단계. 현재 객체 참조로 엮인 그래프를 정리.
  - 경계 결정: `Project`(Root)가 `Recruitment`를 포함하는가, 별도 Aggregate인가? `ProjectMember`는? `RecruitmentState`는?
  - Aggregate 간 직접 객체 참조 → ID 참조 전환 검토.
  - 📄 산출물: `docs/ddd/aggregates.md` + 리팩터링 2차

## 5-3. REPOSITORY
- **[학습]** Repository는 **Aggregate Root 단위**로만 존재. 컬렉션처럼 다루는 추상화.
- **[MeeTeam 적용]** 현재 Repository들이 Aggregate 경계를 침범하지 않는지 점검(`RecruitmentStateRepository` 등이 독립 Root로 적절한지).

## 5-4. SERVICE (Domain Service)
- **[학습]** 한 엔티티에 넣기 애매한 도메인 로직만 Domain Service로. Application Service와 구분.
- **[MeeTeam 적용]** `RecruitmentDomainService` 역할 재정의. Application Service(유스케이스 조율)와 Domain Service(순수 규칙) 분리.

## 5-5. FACTORY
- **[학습]** 복잡한 Aggregate 생성 로직 캡슐화.
- **[MeeTeam 적용]** `ProjectPostCommand` → `Project` Aggregate 조립 로직을 Factory/정적 생성 메서드로 정리.

## 5-6~5-8. 리팩터링 실습 (상품 → 메뉴 → 매장 주문)
- **[학습]** 예제 도메인으로 Entity/VO/Aggregate/Repository/Factory를 단계적으로 적용하는 흐름을 통째로 경험.
- **[MeeTeam 적용]** 예제 대신 **우리 도메인 3종으로 치환**:
  1. 1단계 — `Skill`/`Job`(단순) 리팩터링
  2. 2단계 — `Recruitment`(중간) 리팩터링
  3. 3단계 — `Project`(Root, 복합) 리팩터링

# PART 6. 아키텍처

## 6-1. 계층형 아키텍처
- **[학습]** presentation → application → domain → infrastructure 의존 방향.
- **[MeeTeam 적용]** 현재 `web` / `domain` / `global` 구조를 위 계층과 매핑. 도메인이 인프라를 모르도록 정리.

## 6-2. DTO
- **[학습]** 계층 경계를 넘는 데이터 전달. 도메인 모델 노출 금지.
- **[MeeTeam 적용]** Command DTO는 이미 있음. Response DTO와 엔티티 직접 노출 지점 점검(Swagger 응답 등).

## 6-3. 의존 역전 원칙 (DIP)
- **[학습]** 도메인이 인터페이스를 정의하고 인프라가 구현. 도메인이 JPA/S3에 의존하지 않게.
- **[MeeTeam 적용]** Repository 인터페이스의 위치(도메인 계층) vs 구현(인프라)을 정리. 파일 저장(S3) 추상화 검토.

## 6-4. ANTICORRUPTION LAYER (ACL)
- **[학습]** 외부 시스템/레거시 모델이 우리 도메인을 오염시키지 않도록 번역 계층을 둔다.
- **[MeeTeam 적용]** **세종대 포털 인증**(`SejongPortalClient`)이 1순위 ACL 대상. 외부 인증 응답을 우리 도메인 모델로 번역하는 경계 명시. (S3, RabbitMQ도 후보)
  - 📄 산출물: `docs/ddd/acl.md`

# PART 7. 도메인 이벤트와 CQRS

## 7-1. DOMAIN EVENT
- **[학습]** "도메인에서 의미 있는 사건"을 1급 객체로. 부수효과(알림 등)를 이벤트로 분리.
- **[MeeTeam 적용]** 이미 사용 중인 Spring Event 기반 알림을 **도메인 이벤트로 정식화**.
  - 이벤트 네이밍을 과거형 도메인 용어로(`ProjectMemberJoined`, `ApplicationApproved`).
  - 이벤트 발행 위치를 Aggregate/Application Service로 정리.

## 7-2. 이벤트 소싱 (Event Sourcing)
- **[학습]** 상태가 아니라 이벤트의 연속으로 상태를 재구성. (개념 이해 위주)
- **[MeeTeam 적용]** **도입 보류/검토만.** 현 규모엔 과할 수 있음. 알림/활동 로그 등 일부 영역에 부분 적용 가능성만 메모.

## 7-3. CQRS
- **[학습]** 명령(쓰기 모델)과 조회(읽기 모델) 분리.
- **[MeeTeam 적용]** 이미 `CommandService`/`QueryService`로 분리됨 ✅. 이를 정식 CQRS 관점에서 정리하고, 조회 전용 모델(QueryDSL Projection)과 쓰기 모델(Aggregate)의 책임을 명확히.

## 7-4. ACL 재방문
- **[MeeTeam 적용]** 6-4에서 정의한 ACL을 이벤트/통합 관점에서 보완.

## 결론: 적용 가능한가?

**가능하다.** 다만 "전면 재작성"이 아니라 **파일럿 컨텍스트부터 점진적 리팩터링**으로 접근해야 한다.
이미 도메인 패키지·CQRS 맹아·VO·도메인 이벤트(알림) 자산이 있어 출발점이 좋다.
가장 먼저 할 일은 **(1) 테스트 안전망 확보**와 **(2) 용어 사전/컨텍스트맵 문서화**이며, 이 두 가지가 끝나야
안전하게 전술적 리팩터링(Entity·VO·Aggregate)으로 진입할 수 있다.
