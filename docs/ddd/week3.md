## 0. 왜 마지막이 아키텍처인가 (방향성)

Week 2에서 객체는 똑똑해졌다. 하지만 그 똑똑한 도메인이 여전히 **JPA 어노테이션·S3·외부 API에 직접 묶여** 있으면,
도메인 규칙을 테스트하려면 DB가 떠야 하고, 외부 시스템이 바뀌면 도메인이 흔들린다.
Week 3는 **"순수한 도메인을 세상의 변덕으로부터 보호하는 막"** 을 친다.

```
도메인(규칙) ── 보호막(DIP/ACL) ── 인프라(JPA, S3, 세종대포털, RabbitMQ)
                                    └ 부수효과는 도메인 이벤트로 분리
```

---

## 🧭 큼직한 개념 힌트

- **계층형 아키텍처 & 의존 방향**
  presentation → application → domain → infrastructure. **화살표는 항상 안(도메인)을 향한다.**
  도메인은 바깥(웹·DB)을 몰라야 한다.
- **DTO의 역할**
  계층 경계를 넘는 운반체. **엔티티를 컨트롤러/외부로 직접 노출하지 않는다.** (양방향: 입력 Command, 출력 Response)
- **의존 역전 원칙(DIP)**
  도메인이 인터페이스를 **정의**하고, 인프라가 그걸 **구현**한다. 도메인이 JPA/S3를 import하지 않게.
- **Anticorruption Layer(ACL, 부패 방지 계층)**
  외부 시스템의 모델/언어가 내 도메인을 오염시키지 못하게 **번역하는 경계**. 외부 응답 → 내 도메인 용어로 통역.
- **Domain Event**
  "도메인에서 일어난, 의미 있는 사건"을 1급 객체로. 과거형 이름(`ApplicationAccepted`). 부수효과(알림 등)를 떼어낸다.
- **Event Sourcing** (개념만)
  상태를 저장하는 대신 **사건의 나열**을 저장하고 재생해 상태를 복원. — 강력하지만 무겁다. 도입이 아니라 **이해**가 목표.
- **CQRS**
  명령(쓰기, Aggregate 중심)과 조회(읽기, 화면 맞춤 모델)의 **모델을 분리**. 우리는 이미 절반 와 있다.

## 🎯 미션

### Mission 3-1. 의존 방향 감사 — 도메인은 바깥을 아는가?

- 🔍 도메인 패키지가 인프라/웹을 import하는 곳을 **전부 찾아라**.
  - `grep -rn "import.*jakarta.persistence\|import.*s3\|import.*web" domain/` 같은 식으로.
  - **질문 1**: 도메인 엔티티가 JPA 어노테이션으로 떡칠돼 있다. 이걸 "순수 도메인 + 매핑 분리"로 가는 건 현실적으로 과한가? (정답: 보통 과하다. **현실적 타협선**을 네가 정해라. — 어디까지 허용할지 문서화)
  - **질문 2**: Week 1에서 본 `Project` → `ProjectPostCommand`(서비스 DTO) import는 Week 2에서 풀었나? 다른 곳에 또 있나?
- 🔧 **Repository 인터페이스의 위치**를 점검하라. 인터페이스(추상)는 도메인 가까이, 구현(`...RepositoryImpl`, QueryDSL)은 인프라 성격. 지금 구조가 DIP를 만족하나?
- 📄 산출물: `docs/ddd/dependency-rules.md` (허용/금지 의존 규칙 + 현실적 타협선)

### Mission 3-2. ACL 1순위 — 세종대 포털 통역사

- 🔍 단서: `SejongPortalClient.java` (CLAUDE.md에 언급된 SSL 이슈의 그 클라이언트).
  - 외부 포털의 응답(학번·이름·학과 등 외부 모델)이 **어디서 내 `Member` 도메인으로 바뀌는가**?
  - **질문**: 만약 포털 응답 필드명이 바뀌거나 포털이 교체되면, 그 변경이 `Member`까지 번지나? 번진다면 그 사이에 **번역 계층(ACL)** 이 없다는 뜻이다.
- 🔧 외부 응답 → 도메인 변환을 담당하는 **경계(예: `SejongMemberTranslator`/Adapter)** 를 명시하라. (이미 일부 있으면 그걸 ACL로 승격)
  - **질문**: S3(파일), RabbitMQ(채팅)도 ACL 후보다. 이 중 진짜 보호가 필요한 건 어디인가? 우선순위를 매겨라.
- 📄 산출물: `docs/ddd/acl.md`

### Mission 3-3. 도메인 이벤트 정식화

이미 `@TransactionalEventListener` + `@Async` 로 알림을 쏘고 있다 (`publishApplyNotifications` 등). 이걸 "우연히 이벤트스러운 코드"에서 **정식 도메인 이벤트**로 끌어올린다.

- 🔍 현재 이벤트 발행 지점을 모두 찾아라. 이름이 **명령형/현재형**인가, **과거형 사실**인가?
  - **질문**: `publishApplyNotifications`는 "알림을 보내라"는 명령이다. 도메인 사실은 "지원이 접수되었다(`ApplicationSubmitted`)"이다. 둘의 차이가 왜 중요한가? (힌트: 사실 하나에 부수효과는 여럿 — 알림 + 통계 + 로그)
- 🔧 시범 적용: 지원 수락 흐름 하나를 골라
  1. Aggregate(또는 App Service)가 `ApplicationAccepted` **사실**을 발행하고
  2. 알림은 그 사실을 **구독**해서 처리하도록 분리.
  - **질문**: 발행 위치가 트랜잭션 안인가 커밋 후인가? `@TransactionalEventListener(phase = AFTER_COMMIT)`를 왜 쓰는지 직접 설명해봐. (DB 커밋 전에 알림 나가면 생기는 사고를 상상)
- 📄 산출물: `docs/ddd/domain-events.md` (이벤트 목록 + 발행/구독 매핑)

### Mission 3-4. CQRS 다듬기 (이미 절반 와 있다)

- 🔍 단서: `ProjectCommandService` / `ProjectQueryService` 가 이미 분리돼 있다. `ProjectQueryServiceImpl`(QueryDSL Projection) 를 보라.
  - **질문 1**: 조회는 Aggregate(쓰기 모델)를 거쳐 DTO로 변환하나, 아니면 **DB → 화면 DTO로 바로** 뽑나? 후자가 더 효율적인 경우가 보이나?
  - **질문 2**: 쓰기 모델(Week 2에서 똑똑해진 엔티티)과 읽기 모델(조회 전용 Projection)의 책임이 섞인 곳이 있나?
- 🔧 한 조회 유스케이스를 골라, 읽기 전용 모델을 명확히 분리해보라. (쓰기 규칙이 읽기 경로에 끼어들지 않게)
- **질문(개념 마무리)**: 여기까지 왔으면 Event Sourcing이 왜 "CQRS의 자연스러운 확장이자 과한 선택"인지 한 문단으로 적어라. 우리 프로젝트에 **부분적으로라도** 가치 있는 곳이 있나? (예: 활동/지원 이력)

이벤트 & CQRS:
- [ ] 현재 이벤트 발행 지점을 찾고 이름을 **과거형 사실**로 재정의했다
- [ ] 도메인 사실 발행 ↔ 알림 구독을 분리해 1개 흐름에 시범 적용했다
- [ ] `AFTER_COMMIT`을 쓰는 이유를 내 말로 설명했다
- [ ] 쓰기 모델과 읽기 모델(Projection)의 책임 분리를 1개 유스케이스로 정리했다
- [ ] Event Sourcing의 가치/과함을 우리 프로젝트 맥락에서 판단했다
